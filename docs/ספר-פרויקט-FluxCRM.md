## 1. תיאור ורקע כללי

**FluxCRM** היא מערכת ווב לניהול קשרי לקוחות (CRM) ולניהול פיננסי בסיסי (חשבוניות ותשלומים), המיועדת בעיקר ל**נותני שירות ועסקים קטנים ובינוניים**: פרילנסרים, משרדי ייעוץ, קליניקות, נותני שירותי IT וכדומה.

המערכת מאפשרת לנהל במקום אחד את מאגר הלקוחות, להפיק חשבוניות, לעקוב אחר סטטוס תשלומים, ולצפות בתמונת מצב עסקית באמצעות דשבורד אנליטי. המערכת נבנתה כאפליקציית **Single Page Application** מבוססת דפדפן, עם הפרדה מלאה בין שרת (API) ללקוח (UI).

הפרויקט מבוסס על בסיס הקוד הפתוח **IDURAR ERP/CRM** (רישיון AGPL-3.0), שעליו ביצענו לימוד מעמיק, אבחון, תיקון תקלות, הקשחת אבטחה, ומיתוג מחדש. על גבי בסיס זה פיתחנו תוספות מקוריות משלנו (ראו פרק 4). גישה זו — לימוד מערכת קיימת ברמת קוד המקור והרחבתה — מדמה תרחיש נפוץ בתעשייה שבו מהנדס נכנס למערכת קיימת, לומד אותה, מתחזק ומרחיב אותה.

## 2. מטרות המערכת

מטרת-העל: לספק לנותן השירות כלי פשוט, מהיר ומותאם לשוק המקומי (כולל עברית ו-RTL) לניהול הלקוחות והכספים, ללא המורכבות והעלות של מערכות ERP גדולות.

מטרות מפורטות:

- **ניהול לקוחות** — יצירה, עריכה, חיפוש ומחיקה (רכה) של כרטיסי לקוח.
- **ניהול חשבוניות** — הפקת חשבונית מרובת פריטים, חישוב סכומי ביניים/מס/סה"כ, מעקב סטטוס ותפוגה, ייצוא ל-PDF.
- **ניהול תשלומים** — רישום תשלומים כנגד חשבוניות ומעקב יתרות (שולם/לא שולם/חלקי).
- **תמונת מצב עסקית** — דשבורד אנליטי עם גרפים (סכומי חשבוניות לאורך זמן, פילוח סטטוסים, לקוחות מובילים).
- **נגישות שפה** — ממשק דו-לשוני עברית/אנגלית עם התאמת כיווניות (RTL).
- **אבטחה** — הזדהות מבוססת JWT, סיסמאות מוצפנות (גיבוב), ודרישת הזדהות לכל נקודות ה-API של היישום.

## 3. סקירת מצב קיים בשוק

שוק ה-CRM רווי בפתרונות, אך רובם אינם אופטימליים עבור נותן שירות קטן בישראל:

| מערכת | חוזקות | חסרונות עבור קהל היעד |
|---|---|---|
| Salesforce | עוצמתי, מודולרי | יקר מאוד, מורכב מדי לעסק קטן |
| Zoho CRM | עשיר בפיצ'רים | עקומת למידה, תמחור מדורג, עברית/RTL חלקית |
| Monday.com | חווית משתמש טובה | לא ייעודי לחשבוניות/CRM קלאסי, מנוי חודשי |
| מערכות ישראליות (Powerlink וכו') | תמיכה בעברית | עלות גבוהה, סגור, קשה להתאמה |

**הבעיות המרכזיות בשוק עבור קהל היעד:**
1. **עלות** — רישוי חודשי מצטבר, לא כדאי לעסק קטן.
2. **מורכבות** — פיצ'רים רבים שאינם רלוונטיים לנותן שירות.
3. **תמיכת עברית/RTL** — לעיתים חלקית או לא מלאה.
4. **סגירוּת** — קושי בהתאמה אישית; אין גישה לקוד.

FluxCRM, בהיותה מבוססת קוד פתוח, ניתנת לאירוח עצמי (self-hosting) ללא עלות רישוי, ופתוחה להתאמות.

## 4. חידוש ושיפור — תרומת הפרויקט

זהו לב הפרויקט: מה **אנחנו** תרמנו מעבר לבסיס הקיים. התרומות מתחלקות לשלוש תוספות מקוריות ולעבודת הקשחה ותחזוקה.

### 4.1 תוספות מקוריות (פיתוח עצמאי)

1. **דשבורד אנליטי** — נקודת קצה (endpoint) חדשה בשרת המבצעת אגרגציות ב-MongoDB, ועמוד ייעודי בצד הלקוח עם שלושה גרפים (קו/עוגה/עמודות). ראו פרק 10.
2. **מערכת רב-לשונית עברית/אנגלית עם RTL** — הבסיס תמך למעשה רק באנגלית (מנגנון התרגום היה מנוטרל). הפעלנו מחדש את מנגנון התרגום, בנינו מילון עברי (כ-190 מונחים), הוספנו בורר שפה, ותמיכת כיווניות RTL אוטומטית.
3. **מערך בדיקות אוטומטיות** — לבסיס לא היו בדיקות כלל. בנינו מערך בדיקות יחידה ובדיקות אינטגרציה (Jest + supertest). ראו פרק 14.

### 4.2 הקשחה, תיקונים ותחזוקה

- **תיקון 2 באגים חוסמים** שמנעו הרצה תקינה (ראו P1 ו-P2 בפרק 6).
- **הקשחת אבטחה** — החלפת מפתח JWT מוגדר-מראש (placeholder) במפתח אקראי חזק, הוצאת קובץ הסודות (`.env`) ממעקב הגרסאות, תיקון חבילה פגיעה (multer, CVE-2022-24434).
- **מיתוג מלא** ל-FluxCRM והסרת קישורים מסחריים/פרסומיים של הבסיס.
- **ניקוי קוד מת** (מודול דשבורד לא בשימוש, imports וקוד מוער).

## 5. דרישות מערכת ופונקציונליות

### 5.1 דרישות מערכת (לא-פונקציונליות)

- **סביבת הרצה:** שרת Node.js (גרסאות LTS 20 עד 22; גרסאות 25 ומעלה אינן נתמכות בשל חוסר תאימות של חבילת ה-JWT), מסד נתונים MongoDB, דפדפן מודרני בצד הלקוח.
- **פריסה (Deployment):** אפשרות אירוח מקומי או ענן; בפיתוח — שרת מקומי + MongoDB מקומי.
- **ביצועים:** תגובת API בדרך כלל מתחת ל-200ms לפעולות CRUD (נמדד מקומית: חציון כ-40–140ms; פעולה ראשונה, כגון התחברות, עשויה להימשך מספר שניות); אגרגציית האנליטיקה מבוצעת במסד (pipeline) ולא בקוד היישום, לצמצום העברת נתונים.
- **שרידוּת:** מצב "מחיקה רכה" (`removed: true`) במקום מחיקה פיזית, המאפשר שחזור.
- **התמודדות עם עומסים:** דחיסת תגובות (compression), והגבלת קצב בקשות (rate-limit) על נקודת ההתחברות (20 ניסיונות ל-15 דקות, מענה `429`).
- **אבטחה:** הזדהות מחייבת לכל נקודות ה-API של היישום; סיסמאות מוצפנות (bcrypt).

## 7. הפתרון הטכנולוגי הנבחר

### 7.1 טופולוגיית הפתרון (Deployment)

ארכיטקטורת **שלוש שכבות** (Three-Tier):

```
[ דפדפן / React SPA ]  ⇄  HTTP/REST (JSON)  ⇄  [ Node.js + Express API ]  ⇄  [ MongoDB ]
       שכבת תצוגה                                    שכבת לוגיקה                שכבת נתונים
     (פורט 3000)                                     (פורט 8888)               (פורט 27017)
```

- **שכבת תצוגה:** אפליקציית React הרצה בדפדפן, מתקשרת עם השרת ב-REST.
- **שכבת לוגיקה:** שרת Express החושף REST API, מטפל באימות, בוולידציה ובגישה למסד.
- **שכבת נתונים:** MongoDB (מסד מסמכים).

בפיתוח: כל השלוש רצות על מכונת המפתח (localhost). בפריסה: ניתן להפריד את השרת והמסד לענן.

### 7.2 טכנולוגיות ושפות פיתוח

| שכבה | טכנולוגיה | שפה |
|---|---|---|
| Frontend | React 18, Redux Toolkit, Ant Design, Vite, Ant Design Plots | JavaScript / JSX |
| Backend | Node.js 20, Express 4, Mongoose 8 | JavaScript |
| Database | MongoDB 8 | — |
| בדיקות | Jest, Supertest | JavaScript |
| ניהול גרסאות | Git, GitHub | — |

### 7.3 תיאור הארכיטקטורה

הפרויקט בנוי בגישת **Convention over Configuration**: השרת סורק דינמית את תיקיית המודלים ובונה אוטומטית בקרי CRUD גנריים (`createCRUDController`) ואת נתיבי ה-API לכל ישות (`/api/<entity>/create|read|update|delete|list|search`). לישויות מורכבות (חשבונית, תשלום) קיימים בקרים מותאמים המרחיבים את הגנרי (יצירה, שליחת מייל, סיכום, אנליטיקה).

### 7.3.1 חלופות ארכיטקטוניות שנשקלו

בבחירת הארכיטקטורה ברמת המערכת נבחנו שלוש חלופות:

| חלופה | יתרונות | חסרונות | החלטה |
|---|---|---|---|
| **1. מונוליט MVC** (השרת מרנדר HTML, למשל Express+Pug) | פשוט לפיתוח ולפריסה | צימוד הדוק בין תצוגה ללוגיקה; חווית משתמש עשירה קשה; קשה לשנות UI בנפרד | נדחתה |
| **2. Microservices** (כל תחום כשירות נפרד) | יכולת הרחבה גבוהה, בידוד תקלות | מורכבות תפעולית גבוהה (תזמור, רשת, ניטור), מורכב מדי להיקף הפרויקט | נדחתה |
| **3. שלוש שכבות: SPA + REST API** (React SPA מול שרת REST חסר-מצב) | הפרדת אחריות נקייה; חווית משתמש עשירה; הרחבה עצמאית של הלקוח והשרת; קל לבדיקה | דורש ניהול מצב בצד לקוח וטיפול ב-CORS/אימות token | **נבחרה** |

הארכיטקטורה הנבחרת (שלוש שכבות) מספקת את האיזון הטוב ביותר בין פשטות, חווית משתמש ויכולת הרחבה — ותואמת את בסיס הקוד הקיים.

### 7.4 חלוקה לתוכניות ומודולים

**Backend (`backend/src/`):**
- `models/` — סכמות Mongoose (coreModels, appModels)
- `controllers/` — לוגיקה עסקית (core, app, middlewares, pdf)
- `routes/` — הגדרת נתיבי ה-API
- `middlewares/` — אימות, הגדרות, העלאת קבצים
- `setup/` — סקריפטי אתחול וזריעת נתונים

**Frontend (`frontend/src/`):**
- `pages/` — עמודי היישום (Customer, Invoice, Payment, Analytics, Settings...)
- `modules/` — רכיבי-על (CrudModule, ErpPanelModule, AnalyticsModule...)
- `redux/` — ניהול מצב (auth, crud, settings...)

**מסכים עיקריים:** התחברות, ניהול לקוחות, ניהול חשבוניות (רשימה/יצירה/צפייה/עריכה), ניהול תשלומים, **אנליטיקות**, הגדרות.

בפיתוח: שרת מקומי (Node) + MongoDB מקומי (שירות Windows). ניתן להעביר לפריסת ענן / שירות אירוח בעתיד.

## 10. המרכיב האלגוריתמי־אנליטי

התוספת המקורית המרכזית. נקודת הקצה `GET /api/invoice/analytics` מבצעת שלוש אגרגציות ב-MongoDB ומחזירה מבנה אחד לצריכת הדשבורד.

**איזו בעיה נפתרת?** נותן שירות זקוק לתמונת מצב מהירה: כמה חויבו הלקוחות בכל חודש? כמה חשבוניות בכל סטטוס? מי הלקוחות הכי משתלמים? הבסיס לא סיפק זאת (הדשבורד המקורי הציג רק כרטיסי סיכום, ללא גרפים אמיתיים).

**כיצד נפתר?** באמצעות **Aggregation Pipeline** של MongoDB — החישוב מתבצע במסד ולא בקוד היישום, ליעילות:

1. **סכום חשבוניות לפי חודש (12 חודשים):** סינון לפי טווח תאריכים → קיבוץ (`$group`) לפי שנה+חודש עם `$sum` על ה-`total` → מיון. לאחר מכן, בקוד, בונים **סדרה רציפה של 12 חודשים** כך שחודשים ללא חשבוניות מוצגים כאפס (חשוב לגרף הקו).
2. **פילוח לפי סטטוס:** `$group` לפי `status` עם ספירה — עבור גרף העוגה.
3. **5 לקוחות מובילים:** `$group` לפי לקוח עם `$sum`, מיון יורד, `$limit: 5`, ו-`$lookup` לשליפת שם הלקוח — עבור גרף העמודות.

**קטע קוד מייצג (השרת):**

```javascript
const startDate = moment().subtract(11, 'months').startOf('month').toDate();
const monthlyRaw = await Model.aggregate([
  { $match: { removed: false, date: { $gte: startDate } } },
  { $group: {
      _id: { year: { $year: '$date' }, month: { $month: '$date' } },
      total: { $sum: '$total' }, count: { $sum: 1 },
  } },
  { $sort: { '_id.year': 1, '_id.month': 1 } },
]);
// בניית סדרת 12 חודשים רציפה (חודשים ריקים = 0)
```

**הערה מתודולוגית:** הסכומים מחושבים על כלל החשבוניות שלא נמחקו (`removed: false`), בכל הסטטוסים, ולכן הם מייצגים סכום חשבוניות שהופקו ולא הכנסה שנגבתה בפועל. חישוב הכנסה מדויקת (לפי חשבוניות ששולמו בלבד) מופיע כעבודה עתידית (פרק 16).

בצד הלקוח, עמוד `AnalyticsModule` צורך את הנתונים ומרנדר שלושה גרפים (Line/Pie/Column) בעזרת `@ant-design/plots`, כולל תרגום שמות הסטטוסים לעברית ועטיפה ב-`dir="ltr"` לרינדור תקין תחת RTL.

## 11. אבטחת מידע

| אזור הדורש אבטחה | האיום | המענה במערכת |
|---|---|---|
| חשבונות משתמש | חשיפת סיסמאות | הצפנת סיסמאות ב-**bcrypt** עם **salt** ייחודי; הסיסמה עצמה לעולם אינה נשמרת |
| הזדהות / סשן | גישה לא מורשית ל-API | **JWT** חתום (תוקף 24 שעות, או שנה באפשרות "זכור אותי"); כל נקודות ה-API של היישום מאחורי middleware אימות |
| ניתוק / גניבת token | שימוש ב-token לאחר התנתקות | רשימת **loggedSessions** — token תקף רק אם הוא ברשימת הסשנים הפעילים |
| מפתחות וסודות | דליפת סוד מהקוד | סוד ה-JWT הוחלף במפתח אקראי חזק; קובץ `.env` **הוצא ממעקב git** + `.env.example` כתבנית |
| מסד הנתונים | הזרקת שאילתות (injection) | ולידציה (Joi/Mongoose) + דחיית אופרטורים זדוניים (כגון `$gt`) בפרמטרי הסינון של נקודת הרשימה `/list` (הרחבה לשאר נקודות החיפוש — פרק 16) |
| שרת / API | הצפת בקשות (DoS) / ניחוש סיסמאות | **express-rate-limit** על `/api/login` (20 ניסיונות ל-15 דקות, אחריהם `429`); דחיסת תגובות. הגבלה כללית לשאר נקודות ה-API — פרק 16 |
| חבילות צד ג' | פגיעוּת ידועה | שדרוג `multer` ל-`1.4.5-lts.2` (תיקון CVE-2022-24434) |

**דוגמאות תרחיש → מענה:**
- *תרחיש:* תוקף מנסה לגשת ל-`/api/client/list` ללא token. *מענה:* השרת מחזיר `401 Unauthorized`.
- *תרחיש:* משתמש התנתק, אך תוקף שמר את ה-token. *מענה:* ה-token אינו ב-`loggedSessions` → נדחה.
- *תרחיש:* קלט משתמש מכיל אופרטור MongoDB (`$gt`) בפרמטר הסינון של `/list`. *מענה:* הבקשה נדחית (`400`) לפני הגעה למסד.

### 11.1 חלופות אבטחה שנשקלו

**מנגנון הזדהות (Authentication):**

| חלופה | יתרונות | חסרונות | החלטה |
|---|---|---|---|
| **Session + Cookie בצד שרת** | ביטול טוקן מיידי, מנגנון בשל | מצבי (דורש אחסון סשנים), הרחבה אופקית קשה יותר, חשיפה ל-CSRF | נדחתה |
| **OAuth2 / צד שלישי (Google)** | מוריד אחריות אימות, נוח למשתמש | תלות חיצונית ומורכבות, אינו מתאים לכלי self-hosted לעסק קטן | נדחתה |
| **JWT (טוקן חסר-מצב)** | חסר-מצב, ניתן להרחבה, מתאים ל-SPA+REST | קושי בביטול טוקן — **מוזער** באמצעות רשימת loggedSessions | **נבחרה** |

**אחסון סיסמאות:**

| חלופה | החלטה |
|---|---|
| טקסט גלוי (plaintext) | נדחתה — חשיפה מיידית בדליפת מסד |
| הצפנה סימטרית (הפיכה) | נדחתה — ניתנת לפענוח אם המפתח דולף |
| **גיבוב חד-כיווני bcrypt + salt** | **נבחרה** — אינו הפיך ועמיד מפני טבלאות קשת (rainbow tables) |

## 16. מגבלות ועבודה עתידית

מגבלות מוכרות של הגרסה הנוכחית, ושיפורים מתוכננים:

| # | מגבלה | שיפור מתוכנן |

| 1 | **הגבלת קצב מוגדרת רק על ההתחברות** — שאר נקודות ה-API אינן מוגבלות | הגבלה כללית לכלל ה-API |
